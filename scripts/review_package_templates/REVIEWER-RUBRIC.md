# Reviewer Rubric (shared) — FSI-AgentGov UX Review

{{PROVENANCE}}

You are reviewing a **documentation + governance-tool website** for **US
financial-services M365 administrators** (and secondarily compliance / AI-governance
leads). It is **not** for developers or end users. The owner's concern: the site sees
**low traffic and reads like dry technical documentation** — they want it **useful,
approachable, and engaging** while staying accurate and appropriately hedged on
compliance language ("supports compliance with", not "ensures compliance").

Evaluate your assigned area against these lenses (use the ones that apply):

1. **Information architecture & findability** — grouping, depth, labels, can a user
   locate what they need in ≤3 clicks / one search?
2. **Onboarding / first-run** — can a brand-new admin understand what this is and take
   a first action quickly?
3. **Clarity & scannability** — BLUF-first, plain language, consistent terminology,
   reasonable reading level, skimmable structure (headings, tables, callouts).
4. **Task orientation** — can the user actually *accomplish a goal* (implement a control,
   run the assessment, prep an audit) without friction or dead ends?
5. **Consistency** — template adherence, canonical role names, tone, formatting.
6. **Accessibility** — contrast, headings, link text, alt text, keyboard/structure.
7. **Engagement & value proposition** — does it feel worth using? Is the value clear in
   the first 10 seconds? What makes it read as "technical docs" vs. a useful resource?
8. **Visual & layout** (use `_rendered-site/` + `_pdf/`) — hierarchy, density, whitespace.
9. **Cross-referencing & flow** — do related items connect; is the user's journey coherent?
10. **Discoverability / SEO** (where relevant) — titles, metadata, entry points.

**Ground rules**
- Critique **what exists** and propose **concrete, actionable** improvements. Do not
  redesign the whole product; prioritise high-impact, realistic changes.
- Cite **specific locations** (file + section/page) for every finding.
- Distinguish **must-fix** from **nice-to-have**. Include a short **"what works — keep"** list.
- You have everything you need in the package; no repository access is expected.

Return your findings in **`RESPONSE-TEMPLATE.md`** format.
