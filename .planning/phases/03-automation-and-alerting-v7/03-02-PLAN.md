# Plan 03-02: Adaptive Card Template, Power Automate Flow JSON, and Flow Setup Guide

## Goal

Create the complete automation layer that ties the runbook wrapper (03-01), Dataverse infrastructure (Phase 2), and operator alerting into a daily automated workflow. The flow JSON is the orchestration backbone — it triggers daily, executes the runbook, parses results, writes to Dataverse for audit trail, and routes alerts based on severity. The adaptive card provides rich Teams notifications for content moderation violations. The setup guide ensures operators can deploy and configure the flow.

## Tasks

### Task 1: Create adaptive-card-moderation-alert.json

Create `content-moderation-monitor/src/adaptive-card-moderation-alert.json` following the proven AAM/ACV adaptive card pattern, adapted for per-agent content moderation violations.

**Card structure:**

```
┌─────────────────────────────────────────────┐
│ ⚠ CONTENT MODERATION GOVERNANCE MONITOR     │
│ Severity: ${AlertSeverity}                  │
├─────────────────────────────────────────────┤
│ Run Summary                                 │
│ Time: ${Timestamp}                          │
│ Total Agents: ${TotalAgents}                │
│ Total Environments: ${TotalEnvironments}    │
│ Status: ${OverallStatus}                    │
│ Reason: ${Reason}                           │
├─────────────────────────────────────────────┤
│ Zone Summary                                │
│ Zone 1: ${Z1Compliant}/${Z1Total} agents    │
│ Zone 2: ${Z2Compliant}/${Z2Total} agents    │
│ Zone 3: ${Z3Compliant}/${Z3Total} agents    │
├─────────────────────────────────────────────┤
│ Violations (if any)                         │
│ • ${AgentName} in ${EnvironmentName}        │
│   Zone: ${Zone}                             │
│   Expected Moderation: ${ExpectedLevel}     │
│   Actual Moderation: ${ActualLevel}         │
│   Severity: ${Severity}                     │
│   Regulatory: ${RegulatoryContext}          │
├─────────────────────────────────────────────┤
│ Drift Detection                             │
│ Drifted Agents: ${DriftedAgents}            │
│ • ${DriftAgentName} in ${DriftEnvName}      │
│   Baseline: ${BaselineLevel}               │
│   Current: ${CurrentLevel}                  │
│   Direction: ${Direction}                   │
├─────────────────────────────────────────────┤
│ [View in Power Platform Admin]              │
│ [Run Manual Check] [View Documentation]     │
└─────────────────────────────────────────────┘
```

**Design rules:**
- Adaptive Card schema version 1.4
- Use `${variableName}` convention for all dynamic values
- Severity drives accent color: Critical=attention(red), High=warning(orange), Info=accent(blue)
- Use `ColumnSet` for zone summary table layout (agents not environments as primary metric)
- Use `FactSet` for per-agent violation details including moderation levels and regulatory context
- Action buttons use `Action.OpenUrl` with configurable target URLs
- Card must be valid JSON parseable by Power Automate
- Key difference from AAM: violations show agent-level details (agent name, moderation level) rather than environment-level settings

**Acceptance Criteria:**
- [ ] Valid Adaptive Card JSON (schema 1.4)
- [ ] All dynamic values use `${variableName}` convention
- [ ] Contains sections: header, run summary, zone summary, violations, drift, actions
- [ ] Severity badge uses appropriate colors (Critical=attention, High=warning, Info=accent)
- [ ] Violation details include agent name, environment, zone, expected vs actual moderation level, severity, regulatory context
- [ ] Drift section shows baseline vs current moderation level with direction per agent
- [ ] Action buttons point to Power Platform Admin Center and documentation

### Task 2: Create moderation-validation-flow.json

Create `content-moderation-monitor/src/moderation-validation-flow.json` — the Power Automate cloud flow definition following the proven AAM/ACV pattern.

**Flow structure:**

```
Trigger: Recurrence (Daily, 6:00 AM UTC)
│
├── Initialize_Variables (10 variables)
│   ├── var_DataverseUrl (string)
│   ├── var_TenantId (string)
│   ├── var_ClientId (string)
│   ├── var_CertificateThumbprint (string)
│   ├── var_SubscriptionId (string)
│   ├── var_ResourceGroup (string)
│   ├── var_AutomationAccount (string)
│   ├── var_TeamsGroupId (string)
│   ├── var_TeamsChannelId (string)
│   └── var_ComplianceDistributionList (string)
│
├── Scope_Try
│   ├── Create_Automation_Job
│   │   └── Azure Automation: Create Job
│   │       - RunbookName: "Start-ModerationValidationRunbook"
│   │       - Parameters: TenantId, ClientId, CertificateThumbprint, DataverseUrl
│   │
│   ├── Wait_For_Job
│   │   └── Until loop: Delay 30s → Get_Job_Status, max 2h
│   │
│   ├── Check_Job_Failed
│   │   └── Condition: Job Status = "Failed"
│   │       → Send_Job_Failure_Email → Terminate_Failed
│   │
│   ├── Get_Job_Output
│   │   └── Azure Automation: Get Job Output
│   │
│   ├── Parse_Results
│   │   └── Parse JSON (schema matches CMM runbook output)
│   │       Schema properties: RunType, Timestamp, TotalAgents, TotalEnvironments,
│   │       OverallStatus, Reason, ZoneSummary, Violations[], Drift{}, AlertRequired, AlertSeverity
│   │
│   ├── Write_Validation_History
│   │   └── HTTP POST to {DataverseUrl}/api/data/v9.2/fsi_moderationvalidationhistory
│   │       - fsi_name: "ModerationScan-{Timestamp}"
│   │       - fsi_runid: new GUID (from expression)
│   │       - fsi_overallstatus: body('Parse_Results')?['OverallStatus']
│   │       - fsi_violationcount: length(body('Parse_Results')?['Violations'])
│   │       - fsi_totalagents: body('Parse_Results')?['TotalAgents']
│   │       - fsi_environments_scanned: body('Parse_Results')?['TotalEnvironments']
│   │       - fsi_summaryjson: string(body('Parse_Results'))
│   │       - fsi_validation_time: body('Parse_Results')?['Timestamp']
│   │       connection: fsi_cr_dataverse_moderationmonitor
│   │       runAfter: Parse_Results [Succeeded]
│   │
│   ├── Check_Alert_Required
│   │   └── Condition: body('Parse_Results')?['AlertRequired'] = true
│   │       runAfter: Write_Validation_History [Succeeded, Failed]
│   │
│   ├── If_Alert_Required_True
│   │   ├── Check_Severity_Level
│   │   │   └── Condition: AlertSeverity in (Critical, Failed, Error)
│   │   │
│   │   ├── If_Critical_Failed
│   │   │   ├── Post_Teams_Card
│   │   │   │   └── Teams: Post adaptive card to channel
│   │   │   │       - Card body: adaptive-card-moderation-alert.json with replace() for ${} vars
│   │   │   │       - GroupId: var_TeamsGroupId
│   │   │   │       - ChannelId: var_TeamsChannelId
│   │   │   │       connection: fsi_cr_teams_moderationmonitor
│   │   │   └── Send_Alert_Email
│   │   │       └── Office 365: Send email with violation summary
│   │   │           - To: var_ComplianceDistributionList
│   │   │           connection: fsi_cr_office365_moderationmonitor
│   │   │
│   │   └── If_High_Warning
│   │       └── Send_Warning_Email
│   │           └── Office 365: Send email only (no Teams card)
│   │
│   └── If_Alert_Required_False
│       └── (no action — scan passed, history already written)
│
└── Scope_Catch (runAfter: Scope_Try [Failed, TimedOut])
    └── Send_Critical_Error_Email
        └── Office 365: Send CRITICAL error email
            - Subject: "CRITICAL: CMM Flow Execution Failed"
            - Body: error details from Scope_Try
```

**Key design decisions (carried from AAM/ACV pattern):**
- Write_Validation_History is BEFORE Check_Alert_Required (audit trail first)
- Check_Alert_Required runs after Write_Validation_History with `runAfter: [Succeeded, Failed]` — alerting proceeds even if Dataverse write fails
- Parse_Results JSON schema matches the CMM-specific runbook output (TotalAgents, agent-level violations, agent-level drift)
- Connection references use Phase 2 deployed references: `fsi_cr_dataverse_moderationmonitor`, `fsi_cr_teams_moderationmonitor`, `fsi_cr_office365_moderationmonitor`
- Entity set name: `fsi_moderationvalidationhistory` (matches Phase 2 schema)
- Dataverse write maps to CMM-specific columns (`fsi_totalagents` instead of `fsi_totalenvironments`)

**Acceptance Criteria:**
- [ ] Valid Power Automate flow JSON importable into Power Automate
- [ ] Daily recurrence trigger at 6:00 AM UTC
- [ ] Scope_Try/Scope_Catch error handling pattern
- [ ] Write_Validation_History action writes to Dataverse after every scan (BEFORE alert check)
- [ ] Check_Alert_Required has runAfter [Succeeded, Failed] on Write_Validation_History
- [ ] Alert routing: Critical/Failed/Error → Teams + email; High/Warning → email; Passed → none
- [ ] Scope_Catch sends CRITICAL error email on flow failure
- [ ] Connection references match Phase 2 deployed references
- [ ] Parse_Results schema matches CMM runbook JSON output structure
- [ ] All 10 Initialize_Variable actions present with placeholder values

### Task 3: Create FLOW_SETUP.md

Create `content-moderation-monitor/docs/FLOW_SETUP.md` — step-by-step guide for operators to deploy and configure the automated content moderation validation flow.

**Document structure:**

1. **Overview**
   - Purpose of the automated flow
   - Architecture: Recurrence → Azure Automation → Runbook → Dataverse → Teams/Email

2. **Prerequisites**
   - Azure Automation account with `Start-ModerationValidationRunbook` deployed
   - Power Automate Premium license (Azure Automation connector)
   - Phase 2 Dataverse schema deployed (3 tables, 7 env vars, 3 connection refs)
   - Teams channel created for compliance alerts
   - App registration with certificate for non-interactive auth
   - Required PowerShell modules in Azure Automation: MSAL.PS

3. **Import the Flow**
   - Download `moderation-validation-flow.json` from `src/`
   - Navigate to Power Automate → My Flows → Import → Import Package
   - Select JSON file and configure import settings
   - Note: adjust connection references during import

4. **Configure Variables**
   - `var_DataverseUrl`: Dataverse environment URL (e.g., `https://orgname.crm.dynamics.com`)
   - `var_TenantId`: Azure AD tenant GUID
   - `var_ClientId`: App registration client ID
   - `var_CertificateThumbprint`: Certificate thumbprint for MSAL auth
   - `var_SubscriptionId`: Azure subscription containing Automation Account
   - `var_ResourceGroup`: Resource group containing Automation Account
   - `var_AutomationAccount`: Azure Automation account name
   - `var_TeamsGroupId`: Microsoft 365 group ID for Teams channel (from `fsi_CMM_TeamsGroupId` env var)
   - `var_TeamsChannelId`: Teams channel ID (from `fsi_CMM_TeamsChannelId` env var)
   - `var_ComplianceDistributionList`: Email distribution list for alerts

5. **Bind Connection References**
   - `fsi_cr_dataverse_moderationmonitor` → Dataverse connection (used for validation history writes)
   - `fsi_cr_teams_moderationmonitor` → Teams connection (used for adaptive card posting)
   - `fsi_cr_office365_moderationmonitor` → Office 365 connection (used for email alerts)

6. **Validation History Write**
   - Purpose: every scan result is persisted for regulatory audit trail (FINRA 4511, SEC 17a-3)
   - Table: `fsi_ModerationValidationHistory` (OrganizationOwned, immutable)
   - Why it runs before alerting: ensures audit trail exists even if alert delivery fails
   - Troubleshooting: 403 (security role needs Create on table), 404 (table not deployed), 400 (schema mismatch)

7. **Test the Flow**
   - Manual trigger test: open flow → Run → check run history
   - Verify Dataverse history write: check `fsi_moderationvalidationhistory` table for new record
   - Verify Teams alert delivery: check configured channel for adaptive card
   - Verify email alert: check distribution list inbox
   - Check Azure Automation job output: navigate to Automation Account → Jobs

8. **Baseline Capture**
   - Document how to run `Invoke-ModerationBaselineCapture.ps1` before enabling drift detection
   - Explain that first scan without baselines will show `IsFirstRun=true` for all agents
   - Recommend capturing baseline for all environments before enabling production flow

9. **Troubleshooting**
   - Dataverse write failures: permissions, schema version mismatch, connection reference not bound
   - Azure Automation timeout: runbook execution exceeds 2-hour wait loop
   - Teams channel not found: invalid GroupId/ChannelId, connection reference not authorized
   - Parse JSON schema mismatch: runbook output structure differs from flow schema
   - No violations detected but alert sent: check AlertRequired logic in runbook
   - Drift detection showing all agents as first run: baselines not captured yet

**Acceptance Criteria:**
- [ ] Complete step-by-step instructions from import to test
- [ ] All 10 flow variables documented with descriptions
- [ ] Connection reference binding documented for all 3 references
- [ ] Validation history write section explains audit trail purpose and troubleshooting
- [ ] Baseline capture workflow documented
- [ ] Troubleshooting covers common failure modes with error codes
