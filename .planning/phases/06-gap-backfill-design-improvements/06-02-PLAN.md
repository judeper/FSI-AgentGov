### Task 1: Fix Orphaned Footnote Markers (GBD-07)

**Files to modify:**
- `docs/playbooks/governance-operations/escalation-matrix.md`
- `docs/playbooks/governance-operations/decision-log-schema.md`
- `docs/playbooks/governance-operations/action-authorization-matrix.md`
- `docs/playbooks/advanced-implementations/confidence-and-routing.md`
- `docs/playbooks/advanced-implementations/zone1-min-explainability.md`

**Note:** `dspm-for-ai-policy-pack.md` footnote cleanup is handled in Plan 06-01, Task 4.

**Problem:** Multiple files contain `<sup>[N]</sup>` or `[web:NN]` markers that reference a source numbering system not documented in the repository. No footnotes section exists in any of these files. These markers confuse readers who expect clickable references.

**Changes:**

1. **escalation-matrix.md** — Remove or convert `<sup>[8]</sup>` (×2) and `<sup>[3]</sup>` (×2) markers. These appear in the header/title area and a body section. Since the original source is unknown, convert to inline descriptive context where the marker adds meaning, or remove where it adds no value. For example:
   - If `"regulatory requirement<sup>[3]</sup>"` → `"regulatory requirement (per FINRA 4511 recordkeeping obligations)"`
   - If the marker is purely decorative → remove it

2. **decision-log-schema.md** — Remove or convert `<sup>[3]</sup>` (×1), `<sup>[6]</sup>` (×4), `<sup>[7]</sup>` (×2) markers. These appear near compliance rationale text. Convert to inline regulatory citations where identifiable or remove.

3. **action-authorization-matrix.md** — Remove or convert `<sup>[3]</sup>` (×2) markers.

4. **confidence-and-routing.md** — Remove `[web:87]` and `[web:118]` inline citation markers. These are web reference numbers with no bibliography. Remove them cleanly without leaving awkward punctuation.

5. **zone1-min-explainability.md** — Remove `<sup>[18]</sup>` and `<sup>[19]</sup>` markers.

**Approach for each marker:**
- If the surrounding text provides sufficient context without the marker → remove marker
- If the marker references a recognizable regulation → replace with inline citation
- If the marker is in a section header → always remove (section headers should not have footnotes)

**Acceptance Criteria:**
- Zero `<sup>[` markers remain in the 5 modified files
- Zero `[web:` markers remain in confidence-and-routing.md
- Surrounding text reads naturally without markers
- No regulatory claims are left unsupported by removing a citation (maintain hedged language)
- `mkdocs build --strict` passes

### Task 2: Interlink Spec-Level Playbooks (GBD-05)

**Files to modify:**
- `docs/playbooks/advanced-implementations/confidence-and-routing.md`
- `docs/playbooks/advanced-implementations/human-in-the-loop-triggers.md`
- `docs/playbooks/advanced-implementations/zone1-min-explainability.md`

**Problem:** Three closely related specification documents exist but have no cross-reference sections. Readers following the confidence spec don't discover the HITL triggers spec, and vice versa. Inline mentions like "see confidence spec" in the explainability doc are not actual markdown links.

**Changes:**

1. **confidence-and-routing.md** — Add "Related Specifications" section at the end of the document:
   ```markdown
   ---

   ## Related Specifications

   | Specification | Relationship |
   |--------------|-------------|
   | [Human-in-the-Loop Triggers](human-in-the-loop-triggers.md) | Defines when low-confidence responses require human review — uses confidence thresholds defined in this spec |
   | [Zone 1 Minimum Explainability](zone1-min-explainability.md) | Specifies minimum transparency requirements for confidence scores shown to users |
   ```

2. **human-in-the-loop-triggers.md** — Add "Related Specifications" section at the end:
   ```markdown
   ---

   ## Related Specifications

   | Specification | Relationship |
   |--------------|-------------|
   | [Confidence and Routing](confidence-and-routing.md) | Defines the confidence scoring model and routing thresholds that determine when HITL triggers activate |
   | [Zone 1 Minimum Explainability](zone1-min-explainability.md) | Specifies how HITL decisions and confidence scores are communicated to end users |
   ```

3. **zone1-min-explainability.md** — Add "Related Specifications" section at the end AND fix the inline "see confidence spec" reference (~line 34) to be a proper markdown link:
   - Replace "see confidence spec" → "see [Confidence and Routing](confidence-and-routing.md)"
   - Add at end:
   ```markdown
   ---

   ## Related Specifications

   | Specification | Relationship |
   |--------------|-------------|
   | [Confidence and Routing](confidence-and-routing.md) | Defines the confidence scoring model whose outputs this spec requires to be displayed |
   | [Human-in-the-Loop Triggers](human-in-the-loop-triggers.md) | Defines escalation triggers that may need explainability context when presented to reviewers |
   ```

**Acceptance Criteria:**
- All three spec files have a "Related Specifications" table at the end
- Each table links to the other two specs with relationship descriptions
- Inline "see confidence spec" in zone1-min-explainability.md is a proper link
- `mkdocs build --strict` passes (relative links resolve correctly)

### Task 3: Add FAQ Timeline Reconciliation Note (GBD-06)

**File to modify:** `docs/reference/faq.md`

**Problem:** The FAQ describes an "8-week phased approach" with 4 phases (Weeks 1-2 through Weeks 7-8) while the adoption roadmap uses a different model (Phase 0: 0-60 days, Phase 1: 2-6 months, Phase 2: 6-12 months). The FAQ phases map to Phase 0 of the adoption roadmap, but no reconciliation note explains this relationship. A reader following both documents could be confused by "Phase 1" meaning different things.

**Changes:**

After the FAQ's 8-week phase listing (~line 344), add an informational admonition:

```markdown
!!! info "Relationship to Adoption Roadmap"
    The 8-week implementation phases described above correspond to **Phase 0
    (Foundation)** in the [Adoption Roadmap](../framework/adoption-roadmap.md).
    The roadmap extends the timeline further:

    - **Phase 0 (0-60 days):** Foundation — corresponds to the FAQ phases above
    - **Phase 1 (2-6 months):** Production Readiness — scaling governance to all zones
    - **Phase 2 (6-12 months):** Advanced Governance — mature operations and continuous improvement

    When planning your implementation, use the FAQ's 8-week breakdown for initial
    deployment and the Adoption Roadmap for long-term program planning.
```

**Acceptance Criteria:**
- FAQ contains `!!! info "Relationship to Adoption Roadmap"` admonition
- Admonition links to `../framework/adoption-roadmap.md`
- Phase mapping is clearly stated (FAQ 8-week = Roadmap Phase 0)
- `mkdocs build --strict` passes

### Task 4: Remove Quick-Start Emojis (GBD-08)

**File to modify:** `docs/getting-started/quick-start.md`

**Problem:** Section headers use emoji prefixes (🚀, 📋, 📚, 🔑, ✅, 💬) which are inconsistent with the rest of the documentation framework. Professional FSI documentation should rely on clear headings without decorative characters.

**Changes:**

Replace the following section headers:

| Current | Replacement |
|---------|------------|
| `## 🚀 For New Users (10 minutes)` | `## For New Users (10 minutes)` |
| `## 📋 For Implementation (20 minutes)` | `## For Implementation (20 minutes)` |
| `## 📚 Where to Find Things` | `## Where to Find Things` |
| `## 🔑 Key Terms (Quick Version)` | `## Key Terms (Quick Version)` |
| `## ✅ Next Steps` | `## Next Steps` |
| `## 💬 Still Questions?` | `## Still Questions?` |

**Note:** ✅ checkmarks in the regulatory checklist items (~lines 81-90) should be left as-is if they serve as visual indicators in a checklist context, or removed for consistency. Prefer removal for consistency with the rest of the framework.

**Acceptance Criteria:**
- No emoji characters in section headers of `quick-start.md`
- Section header text is otherwise unchanged
- `mkdocs build --strict` passes
