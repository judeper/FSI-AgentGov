### Task 1: Create CAA Deployment Guide (GBD-01)

**Files to create:**
- `docs/playbooks/advanced-implementations/conditional-access-automation/index.md`
- `docs/playbooks/advanced-implementations/conditional-access-automation/deployment-guide.md`

**File to modify:** `mkdocs.yml`

**Problem:** The Conditional Access Automation (CAA) solution has scripts (`Start-CAAValidationRunbook.ps1`, `Test-PolicyCompliance.ps1`, `caa_client.py`, `CAAClient.psm1`, `Compare-PolicyBaseline.ps1`, `Get-PolicyBaseline.ps1`) and a module manifest (`conditional-access-automation.psd1`) but no unified deployment guide explaining how to deploy and configure the end-to-end solution.

**Changes:**

1. **Create `index.md`** — Overview document following the DEC/ELM pattern:
   - Purpose: Automated CA policy compliance validation for Controls 1.11 (CA/MFA), 1.23 (Entra Security Posture), 1.18 (Agent Authentication)
   - Problem Statement: Manual CA policy review doesn't scale; drift detection requires daily automated validation
   - Solution Overview: Azure Automation runbook runs `Test-PolicyCompliance.ps1` daily → evaluates CA policies against zone-specific baselines → persists results to Dataverse → generates compliance reports
   - Architecture diagram (mermaid): Azure Automation → Test-PolicyCompliance.ps1 → Graph API → Policy evaluation → Dataverse persistence → Teams alerting
   - Component table:
     - `Start-CAAValidationRunbook.ps1` — Azure Automation entry point
     - `Test-PolicyCompliance.ps1` — Core compliance validation logic
     - `CAAClient.psm1` — Dataverse persistence module
     - `Compare-PolicyBaseline.ps1` — Baseline drift comparison
     - `Get-PolicyBaseline.ps1` — Baseline snapshot capture
     - `caa_client.py` — Dataverse schema deployment
   - Playbook Structure table (2 entries: Overview, Deployment Guide)
   - Prerequisites: M365 E5, Azure Automation account, Power Platform environment with Dataverse, Entra ID app registration
   - Getting Started steps
   - Footer: `*FSI Agent Governance Framework v1.2.38 - February 2026*`

2. **Create `deployment-guide.md`** — End-to-end deployment following DEC pattern:
   - Phase 1: Prerequisites & App Registration
     - Create Entra ID app registration with Microsoft Graph `Policy.Read.All`, `Application.Read.All` permissions
     - Generate certificate for Azure Automation authentication
     - Upload certificate to app registration and Azure Automation
   - Phase 2: Dataverse Schema Deployment
     - Run `python scripts/caa_client.py` to create Dataverse tables (`fsi_conditionalaccess_result`, `fsi_policy_baseline`)
     - Verify schema deployment with Power Apps model-driven app
   - Phase 3: Module Installation
     - Copy `scripts/private/` helpers to Azure Automation modules
     - Import `conditional-access-automation.psd1` manifest
     - Install Graph module dependencies (`Microsoft.Graph.Identity.SignIns`, `Microsoft.Graph.Applications`)
   - Phase 4: Runbook Configuration
     - Import `Start-CAAValidationRunbook.ps1` as Azure Automation runbook
     - Configure runbook parameters: `$TenantId`, `$ClientId`, `$CertThumbprint`, `$DataverseUrl`
     - Create daily schedule (recommended: 02:00 UTC)
   - Phase 5: Validation
     - Manual test run of runbook
     - Verify Dataverse rows created
     - Verify Teams notification delivery (if configured)
   - Troubleshooting section with common issues
   - Footer

3. **Update `mkdocs.yml`** — Add nav entries after "Agent 365 Observability" section (~line 555):
   ```yaml
   - Conditional Access Automation:
     - Overview: playbooks/advanced-implementations/conditional-access-automation/index.md
     - Deployment Guide: playbooks/advanced-implementations/conditional-access-automation/deployment-guide.md
   ```

**Acceptance Criteria:**
- `docs/playbooks/advanced-implementations/conditional-access-automation/index.md` exists with Purpose, Problem Statement, Solution Overview, architecture diagram, component table
- `docs/playbooks/advanced-implementations/conditional-access-automation/deployment-guide.md` exists with 5-phase deployment instructions

### Task 2: Document ELM Approval Flow (GBD-02)

**File to create:** `docs/playbooks/advanced-implementations/environment-lifecycle-management/implementation-approval.md`

**Files to modify:**
- `docs/playbooks/advanced-implementations/environment-lifecycle-management/index.md`
- `mkdocs.yml`

**Problem:** ELM architecture defines the state machine (Draft → Submitted → PendingApproval → Approved/Rejected → Provisioning) and the intake doc briefly references steps 5-8 for approval, but no dedicated document explains how to build the Power Automate Approval flow that connects intake to provisioning.

**Changes:**

1. **Create `implementation-approval.md`** — Following the pattern of `implementation-copilot-intake.md` and `implementation-provisioning.md`:
   - Header: Status, Related Controls (2.2, 2.8, 2.3)
   - Overview: The approval flow is triggered when the intake agent sets `er_state = 'Submitted'`, routes the request to the appropriate approver(s) based on zone classification, and updates state to `Approved` or `Rejected`
   - Architecture diagram (mermaid): Dataverse trigger → Zone classification check → Approver routing → Power Automate Approval action → State update → Notification
   - Trigger Configuration:
     - "When a row is added or modified" trigger on `EnvironmentRequest` table
     - Filter: `er_state eq 'Submitted'`
   - Approval Routing Logic:
     - Zone 1: Auto-approve (no human approval needed)
     - Zone 2: Single approver (Power Platform Admin)
     - Zone 3: Multi-level approval (Power Platform Admin + Compliance Officer)
   - Approval Action Configuration:
     - Create an Approval (type: "Approve/Reject - First to respond" for Zone 2, "Approve/Reject - Everyone must approve" for Zone 3)
     - Configure approval details (title, details showing request fields, assigned-to from zone lookup)
   - State Update:
     - On Approve: Update `er_state` to `PendingApproval` → `Approved`, set `er_approved_by`, `er_approved_date`
     - On Reject: Update `er_state` to `Rejected`, set `er_rejection_reason`
   - Notification Configuration:
     - Teams message to requester on approval/rejection
     - Include environment details and next steps link
   - Error Handling:
     - Approval timeout (72-hour SLA for Zone 3)
     - Escalation path for stale approvals
   - Footer: `*FSI Agent Governance Framework v1.2.38 - February 2026*`

2. **Update ELM `index.md`** — Add row to Playbook Structure table (~line 195):
   ```markdown
   | [Approval Flow](implementation-approval.md) | Approval routing by zone with multi-level support |
   ```
   Insert between "Copilot Intake Agent" and "Provisioning Flows" rows.

3. **Update `mkdocs.yml`** — Add nav entry after "Copilot Intake Agent" (~line 559):
   ```yaml
   - Approval Flow: playbooks/advanced-implementations/environment-lifecycle-management/implementation-approval.md
   ```

**Acceptance Criteria:**
- `implementation-approval.md` exists with trigger configuration, zone-based routing, multi-level approval, state updates
- ELM `index.md` Playbook Structure table includes Approval Flow entry
- `mkdocs.yml` nav includes Approval Flow between Copilot Intake Agent and Provisioning Flows
- `mkdocs build --strict` passes
- Document uses hedged language ("supports," "helps meet")

### Task 3: Add P4 Portal Walkthrough Caveats (GBD-03)

**Files to modify:**
- `docs/playbooks/control-implementations/4.1/portal-walkthrough.md`
- `docs/playbooks/control-implementations/4.2/portal-walkthrough.md`
- `docs/playbooks/control-implementations/4.6/portal-walkthrough.md`
- `docs/playbooks/control-implementations/4.7/portal-walkthrough.md`

**Problem:** Parent controls document operational caveats (reindexing latency, EEEU risk, discovery amplification) but the portal walkthroughs omit these warnings. An administrator following the walkthrough may not understand the operational implications of the configurations they're enabling.

**Changes:**

1. **4.1 portal-walkthrough.md** — After the step where Restricted Content Discovery (RCD) is enabled, add:
   ```markdown
   !!! warning "Reindexing Latency"
       Enabling Restricted Content Discovery triggers a site reindexing process.
       Full reindex completion can take **24-72 hours** depending on site size.
       Information barriers and sensitivity label-based access restrictions will
       not take effect until reindexing completes. Plan for this delay in your
       rollout schedule. See [Control 4.1](../../../controls/pillar-4-sharepoint/4.1-sharepoint-information-access-governance-iag-restricted-content-discovery.md) for details.
   ```

2. **4.2 portal-walkthrough.md** — In the Data Access Governance (DAG) reports section, add:
   ```markdown
   !!! warning "EEEU (Everyone Except External Users) Priority"
       Sites shared with "Everyone except external users" represent the highest
       oversharing risk for Copilot and should be prioritized for access review.
       EEEU-shared content is accessible to all internal users including Copilot,
       which can surface sensitive data in AI-generated responses. See
       [Control 4.7](../../../controls/pillar-4-sharepoint/4.7-microsoft-365-copilot-data-governance.md)
       for EEEU risk assessment guidance.
   ```

3. **4.6 portal-walkthrough.md** — After grounding scope configuration steps, add:
   ```markdown
   !!! warning "Reindexing After Scope Changes"
       Changes to Copilot grounding scope (adding or removing sites, libraries)
       may trigger partial reindexing. Updated semantic index boundaries become
       effective only after reindex completion. Allow **24-48 hours** before
       validating scope changes via test queries.
   ```

4. **4.7 portal-walkthrough.md** — Add two caveats:
   ```markdown
   !!! warning "EEEU Risk — Discovery Amplification"
       Microsoft 365 Copilot can surface content shared with "Everyone except
       external users" (EEEU) across the organization. This **discovery
       amplification** means that content previously obscure (but technically
       accessible) becomes easily discoverable through natural language queries.
       Review and remediate EEEU sharing before enabling Copilot for sensitive
       sites. Use [Control 4.2 (Site Access Reviews)](../../../controls/pillar-4-sharepoint/4.2-site-access-reviews-and-certification.md)
       DAG reports to identify affected sites.
   ```

**Acceptance Criteria:**
- 4.1 portal-walkthrough has reindexing latency warning
- 4.2 portal-walkthrough has EEEU priority warning
- 4.6 portal-walkthrough has reindexing after scope changes warning
- 4.7 portal-walkthrough has discovery amplification warning
- All warnings use `!!! warning` MkDocs admonition format
- All warnings reference parent controls with relative links
- `mkdocs build --strict` passes

### Task 4: Add DSPM Portal Deployment Steps (GBD-04)

**File to modify:** `docs/playbooks/advanced-implementations/dspm-for-ai-policy-pack.md`

**Problem:** The DSPM policy pack document has prerequisites, rollout strategy, policy list, and scoping rules but no portal step-by-step deployment instructions. An administrator reading the document cannot determine how to access the DSPM for AI portal or create the recommended policies.

**Changes:**

Insert a "Portal Deployment Steps" section after the prerequisites section and before the rollout strategy. The section should include:

1. **Portal Navigation:**
   ```markdown
   ### Step 1: Access DSPM for AI

   1. Navigate to **purview.microsoft.com**
   2. Select **Solutions** > **DSPM for AI** from the left navigation
   3. Select **Overview** to confirm your tenant has DSPM for AI enabled
   4. Select **Policies** to view existing and available policies
   ```

2. **Enable Default Policies:**
   ```markdown
   ### Step 2: Enable One-Click Policies

   DSPM for AI provides pre-built policies that can be activated with a single click.
   For each policy in the rollout schedule below:

   1. Select the policy from the **Policies** page
   2. Review the policy description and scope
   3. Select **Turn on policy** (or **Create policy** for customizable variants)
   4. Configure scope per the zone assignment in the Scoping Rules section below
   5. Select **Save**
   ```

3. **Verification:**
   ```markdown
   ### Step 3: Verify Policy Activation

   1. Return to **DSPM for AI** > **Policies**
   2. Confirm each enabled policy shows **Status: On**
   3. Allow **24-48 hours** for initial policy evaluation
   4. Check **DSPM for AI** > **Reports** for first data points
   ```

4. **Cross-reference to Control 1.6 portal walkthrough:**
   ```markdown
   !!! tip "Detailed DSPM Configuration"
       For foundational DSPM for AI setup, including data classification and
       sensitivity labels, see the [Control 1.6 Portal Walkthrough](../control-implementations/1.6/portal-walkthrough.md).
   ```

Additionally, clean up any orphaned `<sup>[N]</sup>` footnote markers in this file (addressing the GBD-07 overlap for this specific file). Replace orphaned markers with inline descriptive text or remove if they add no context.

**Acceptance Criteria:**
- `dspm-for-ai-policy-pack.md` has "Portal Deployment Steps" section with Steps 1-3
- Portal path uses correct URL (`purview.microsoft.com > Solutions > DSPM for AI`)
- Cross-reference to Control 1.6 portal walkthrough included
- No orphaned `<sup>[N]</sup>` markers remain
