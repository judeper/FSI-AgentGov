**relationships.tmdl:**

Define all relationships between fact and dimension tables. Use TMDL relationship syntax:

```
relationship RelationshipName
    fromTable: SourceTable
    fromColumn: SourceColumn
    toTable: TargetTable
    toColumn: TargetColumn
    crossFilteringBehavior: singleDirection  /// or bothDirections
    isActive: true  /// mark inactive relationships explicitly
```

**Required relationships:**

FactAgentSessions relationships (all active):
1. FactAgentSessions[SessionDate] → DimDate[Date] (many-to-one, single direction)
2. FactAgentSessions[AgentId] → DimAgent[AgentId] (many-to-one, single direction)
3. FactAgentSessions[ZoneId] → DimZone[ZoneId] (many-to-one, single direction)

FactAgentEvents relationships:
4. FactAgentEvents[EventDateKey] → DimDate[DateKey] (many-to-one, single direction, **INACTIVE** — per anti-pattern: mark inactive to avoid ambiguous DimDate relationship with FactAgentSessions. Use USERELATIONSHIP() in DAX measures for event date filtering)
5. FactAgentEvents[AgentId] → DimAgent[AgentId] (many-to-one, single direction)
6. FactAgentEvents[ErrorCategoryId] → DimErrorCategory[ErrorCategoryId] (many-to-one, single direction)
7. FactAgentEvents[UserId] → DimUser[UserId] (many-to-one, single direction)
8. FactAgentEvents[ControlId] → DimControl[ControlId] (many-to-one, single direction)

DimAgent to DimZone bridge:
9. DimAgent[ZoneId] → DimZone[ZoneId] (many-to-one, single direction)

DimUser to DimZone bridge:
10. DimUser[ZoneId] → DimZone[ZoneId] (many-to-one, single direction)

**NOTE:** FactAgentEvents[EventDateKey] → DimDate[DateKey] is marked `isActive: false` to avoid ambiguity. DAX measures that need event-date filtering use `USERELATIONSHIP(FactAgentEvents[EventDateKey], DimDate[DateKey])`.

There is NO direct relationship between DimRegulation and DimControl in the model — the regulation-to-control mapping is handled via a bridge pattern in DAX measures referencing governance-mapping.md data. This keeps the model flexible as mappings evolve.

**ZoneBasedAccess.tmdl:**

Create dynamic RLS role applied to DimZone table:

```
role ZoneBasedAccess

    modelPermission: read

    tablePermission DimZone
        filterExpression:
            IF(
                LOOKUPVALUE(
                    UserZoneMapping[ZoneId],
                    UserZoneMapping[UserEmail],
                    USERNAME()
                ) = DimZone[ZoneId],
                TRUE(),
                FALSE()
            )
```

Key design decisions per locked decisions and research:
- Apply filter to DimZone (dimension), NOT fact tables — relationship propagation handles filtering
- Default to FALSE() for unmatched users (secure default)
- Single role definition — dynamic USERNAME() avoids role proliferation
- UserZoneMapping table referenced (defined in Task 1 within DimUser.tmdl or as separate calculated table)
