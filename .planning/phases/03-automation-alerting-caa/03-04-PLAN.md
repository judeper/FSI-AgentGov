# Plan 03-04: ELM Provisioning Hook Flow

## Objective

Create a Power Automate child flow triggered by the ELM ProvisioningCompleted event that runs a targeted CA policy compliance check for the newly provisioned environment's zone, verifying that zone-appropriate CA policies exist, are enabled, and meet security requirements.

## Requirements Covered

- **AUT-04**: ELM provisioning hook for auto-deploying zone-appropriate CA policies to newly provisioned environments

## Must-Haves Covered

| # | Must-Have | How |
|---|----------|-----|
| 4 | ELM provisioning hook verifying zone CA policy coverage on new environment provisioning | Child flow receives zone classification from ELM, triggers targeted Azure Automation runbook execution scoped to the zone, writes verification results to Dataverse, sends zone-severity alerts for gaps |

## Design Note — Verify-on-Provision Pattern

CAA operates at the **Entra ID tenant level** — CA policies target applications and security groups, not individual Power Platform environments. When a new environment is provisioned:

1. The environment receives a zone classification from ELM
2. CA policies for that zone **should already exist** (deployed once, tenant-wide)
3. The hook verifies that zone coverage is intact, not deploys per-environment policies

This is a **verify-on-provision** pattern, not deploy-on-provision. If verification detects missing zone policies (rare — only occurs if initial setup was incomplete), the alert instructs the operator to run `Deploy-CAPolicies.ps1` manually.

## Tasks

### Task 1: Create child flow JSON scaffold
**File:** `src/caa-provisioning-hook-flow.json`
- Flow type: Child flow (manually triggered with input parameters)
- Display name: `CAA - Provisioning Hook`
- Input parameters:
  - `EnvironmentId` (String) — newly provisioned environment GUID
  - `EnvironmentName` (String) — display name
  - `Zone` (Integer) — zone classification (1, 2, or 3)
  - `ProvisionedBy` (String) — requesting user
  - `ProvisionedAt` (String) — ISO 8601 timestamp
- Connection references:
  - `fsi_cr_dataverse_conditionalaccessautomation`
  - `fsi_cr_teams_conditionalaccessautomation`
  - `fsi_cr_office365_conditionalaccessautomation`

### Task 2: Zone-scoped CA policy verification via Azure Automation
- Create Azure Automation job running `Start-CAAValidationRunbook` with zone filter:
  - Parameter: `-Zone ${Zone}` — restricts compliance checks to the provisioned zone
  - Parameter: `-Scope Targeted` — indicates provisioning-triggered (not daily full scan)
- Poll job completion (30s intervals, 30min timeout — shorter than daily scan)
- Parse JSON output (same schema as daily scan, filtered to zone)

### Task 3: Evaluate verification results
- Parse zone-specific results from runbook output
- Determine verification outcome:
  - **All Clear**: Zone policies exist, enabled, break-glass intact, controls correct
  - **Gaps Found**: Missing policies, disabled policies, weakened controls
  - **Error**: Runbook execution failure

### Task 4: Write verification record to Dataverse
- **Note:** The runbook (Plan 03-01) writes the `fsi_CAPolicyValidationHistory` record with `-Scope Targeted` tag during execution (audit-first, crash-safe). The hook flow verifies the record exists.
- Query `fsi_CAPolicyValidationHistory` to confirm the runbook's record was created:
  - Filter: `fsi_validation_time ge {currentTimestamp}` with provisioning context
  - If record missing (runbook crashed before write): create fallback record with:
    - `fsi_validation_time`: current timestamp
    - `fsi_total_policies`: zone-scoped policy count
    - `fsi_passed_count` / `fsi_failed_count`: zone results
    - `fsi_results_json`: include `EnvironmentId`, `EnvironmentName`, `Scope: Targeted` for traceability

### Task 5: Write violations to Dataverse (if gaps found)
- For each gap detected, create `fsi_CAPolicyViolation` record:
  - `fsi_violation_type`: specific gap (PolicyMissing, PolicyDisabled, etc.)
  - `fsi_zone`: provisioned zone
  - Tag as provisioning-triggered for audit trail

### Task 6: Alert routing based on zone severity
- **Zone 3 (Enterprise Managed)**: CRITICAL severity
  - Teams adaptive card with CRITICAL badge
  - Email to compliance distribution list
  - Message includes: "Zone 3 environment provisioned — CA policy gaps detected. Run Deploy-CAPolicies.ps1 -Zone 3 to remediate."
- **Zone 2 (Team Collaboration)**: HIGH severity
  - Teams adaptive card with HIGH badge
  - Email notification
- **Zone 1 (Personal Productivity)**: WARNING severity
  - Teams adaptive card with WARNING badge
  - Email notification (lower priority)
- **All Clear** (any zone): No alert sent
  - Verification record logged silently

### Task 7: Return output to parent flow
- Child flow output:
  - `VerificationStatus` (String): `Passed`, `Failed`, `Error`
  - `GapsFound` (Integer): count of gaps
  - `AlertSent` (Boolean): whether alert was dispatched
  - `Severity` (String): `Critical`, `High`, `Warning`, or `Passed`
