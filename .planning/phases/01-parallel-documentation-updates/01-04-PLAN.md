# Plan 01-04: Multi-Source Governance Agent Investigation

## Goal

Produce an investigation report evaluating three architectural approaches (MCP Server, Copilot Studio Agent, Hybrid) for a multi-source citation agent that can answer FSI governance questions grounded in framework documentation, Microsoft Learn docs, and regulatory sources. Deliver a clear build/don't-build/defer recommendation with estimated effort if applicable.

## Requirements Covered

FCR-13, FCR-14

## Context

The FSI Agent Governance Framework (62 controls, 248+ playbooks, 13 solutions, 7+ regulations) is consumed only through static MkDocs web pages. The investigation determines whether a conversational interface backed by multi-source citations would provide meaningfully better outcomes for M365 administrators and compliance officers.

**This is an investigation-only deliverable.** No framework documentation is modified. No solution code is built. The output is a planning artifact.

## Tasks

### Task 1: Options analysis — MCP Server, Copilot Studio Agent, Hybrid

**Action:** Analyze three approaches defined in the todo:

**Option A: MCP Server for Framework + External MCP Servers**
- Build custom MCP server exposing FSI-AgentGov content as structured resources/tools
- Integrate Microsoft Learn MCP server for official documentation
- Add regulatory site access (FINRA/SEC) for citation grounding
- Evaluate: MCP ecosystem maturity, build complexity, maintenance cost, client compatibility

**Option B: Copilot Studio Agent with Knowledge Sources**
- Use GitHub Pages site as website knowledge source
- Supplement with uploaded structured data (control index, regulatory mappings)
- System prompt with regulatory language guardrails
- Evaluate: citation quality, knowledge source limitations, single-client constraint, deployment model

**Option C: Hybrid — MCP Server + Copilot Studio Agent**
- MCP server for developer/tool integration
- Copilot Studio agent for end-user Q&A
- Both consume same verified source content
- Evaluate: total build/maintenance cost vs. incremental value over B alone

**For each option, analyze:**
- Build effort (person-days)
- Maintenance burden (monthly hours)
- Citation quality potential (HIGH/MEDIUM/LOW)
- Audience coverage (which target users served)
- Technical feasibility risks
- Pros and cons

**Acceptance criteria:**
- [ ] All 3 options analyzed with consistent evaluation criteria
- [ ] Pros/cons documented for each
- [ ] Effort estimates provided

### Task 2: Key questions analysis

**Action:** Answer the 6 key questions from the todo:

1. **Is it overkill?** Assess whether citation architecture provides meaningfully better answers than existing MkDocs site
2. **GitHub repos as knowledge source** — Is pointing an agent directly at the repos effective for reasoning, or is structured extraction needed?
3. **Learn MCP server value** — Does supplementing with Learn docs improve answer quality enough to justify integration?
4. **Regulatory site access** — Can we reliably extract and cite FINRA/SEC content?
5. **Build vs. buy** — Are there existing tools or services that solve parts of this?
6. **Maintenance burden** — Who keeps the agent/MCP server in sync with framework updates?

**Acceptance criteria:**
- [ ] All 6 questions answered with analysis
- [ ] Each answer includes confidence level (HIGH/MEDIUM/LOW)

### Task 3: Produce recommendation report

**Output file:** `.planning/phases/01-parallel-documentation-updates/01-04-investigation-report.md`

**Action:** Write the investigation report with:

1. **Executive Summary** — 2-3 sentence recommendation
2. **Options Analysis** — From Task 1 (structured comparison table)
3. **Key Questions Analysis** — From Task 2
4. **Recommendation** — Clear build / don't-build / defer with justification
5. **If build or defer:**
   - Recommended approach (A, B, or C) with justification
   - Estimated total effort (person-days)
   - Estimated monthly maintenance cost
   - Recommended milestone for implementation (v10+)
   - Prerequisites and dependencies
6. **If don't-build:**
   - Why the current MkDocs approach is sufficient
   - Alternative low-effort improvements to existing docs

**Report format:** Markdown with YAML frontmatter (`phase: 1`, `plan: 4`, `type: investigation`)

**Acceptance criteria:**
- [ ] Report contains all 6 sections
- [ ] Recommendation is unambiguous (exactly one of: build, don't-build, defer)
- [ ] If build/defer: effort estimate and recommended approach included
- [ ] Analysis is balanced and considers both value and costs
- [ ] No commitment language ("will build") — recommendation only
