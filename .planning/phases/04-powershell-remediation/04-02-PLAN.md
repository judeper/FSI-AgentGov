## Tasks

### Task 1: Test scaffold and mock data

**Action:** Create `scripts/governance/Set-InactivityTimeout.Tests.ps1` with `BeforeAll` setup.

**Details:**
- `#Requires -Version 7.0`
- `#Requires -Modules Pester`
- `BeforeAll` block:
  - `$script:scriptPath = Join-Path $PSScriptRoot 'Set-InactivityTimeout.ps1'`
  - `$script:testToken = 'mock-access-token-12345'`
  - Mock response data:
    - `$script:mockPrivacyDisabled` — timeout disabled (before remediation)
    - `$script:mockPrivacyEnabled` — timeout enabled at 120/5 (after remediation)
    - `$script:mockPrivacyCustom` — timeout enabled at 60/10 (existing custom config)
  - `$script:testEnvironmentName = 'e1234567-89ab-cdef-0123-456789abcdef'`
  - `$script:testDataverseUrl = 'https://org12345.crm.dynamics.com/'`

**Acceptance criteria:**
- [ ] `#Requires -Version 7.0` and `#Requires -Modules Pester` present
- [ ] Mock data defines pre-PATCH and post-PATCH response shapes
- [ ] Test environment name uses canonical format

### Task 2: Parameter validation tests

**Action:** Describe block for parameter validation.

**Tests:**
1. `EnvironmentName is mandatory` — invoke without it should throw
2. `TimeoutDuration defaults to 120` — inspect parameter metadata
3. `TimeoutDuration rejects value below 5` — should throw ParameterBindingValidationException
4. `TimeoutDuration rejects value above 120` — should throw ParameterBindingValidationException
5. `WarningDuration defaults to 5` — inspect parameter metadata
6. `WarningDuration rejects value below 1` — should throw
7. `WarningDuration rejects value above 30` — should throw

**Pattern:** Use `(Get-Command $script:scriptPath).Parameters` to inspect metadata without executing the script.

**Acceptance criteria:**
- [ ] 7 parameter validation tests
- [ ] Tests use parameter metadata inspection (no API calls)

### Task 3: BAP API interaction tests

**Action:** Describe block for GET and PATCH operations.

**Tests:**
1. `Calls GET privacy settings with correct URL` — Mock `Invoke-RestMethod`, verify URI contains EnvironmentName and `/settings/privacy`
2. `Calls PATCH with correct body` — Mock `Invoke-RestMethod` with method filter for PATCH, capture body, verify `InactivityTimeoutEnabled`, `InactivityTimeoutInMinutes`, `InactivityWarningInMinutes`
3. `Handles 404 with environment not found error` — Mock throws HttpResponseException with 404, verify descriptive error message
4. `Handles 401 with auth guidance` — Mock throws 401, verify error includes "Connect-AzAccount" guidance
5. `Handles 403 with permission guidance` — Mock throws 403, verify error includes admin role guidance

**Mock strategy:**
- Mock `Get-AzAccessToken` globally → returns `[PSCustomObject]@{ Token = $script:testToken }`
- Mock `Invoke-RestMethod` with `-ParameterFilter { $Method -ne 'Patch' }` for GET → returns `$script:mockPrivacyDisabled`
- Mock `Invoke-RestMethod` with `-ParameterFilter { $Method -eq 'Patch' }` for PATCH → returns `$script:mockPrivacyEnabled`

**Acceptance criteria:**
- [ ] 5 API interaction tests
- [ ] GET and PATCH mocks correctly separated by method filter
- [ ] Error handling tests cover 401, 403, 404
- [ ] Tests use `-Confirm:$false` to suppress ShouldProcess prompts

### Task 4: WhatIf support tests

**Action:** Describe block for `-WhatIf` behavior.

**Tests:**
1. `-WhatIf does NOT invoke PATCH` — invoke with `-WhatIf`, assert `Should -Not -Invoke Invoke-RestMethod -ParameterFilter { $Method -eq 'Patch' }`
2. `-WhatIf still executes GET` — invoke with `-WhatIf`, assert `Should -Invoke Invoke-RestMethod -ParameterFilter { $Method -ne 'Patch' }` at least once
3. `-WhatIf returns result with Applied = $false` — verify result object

**Acceptance criteria:**
- [ ] 3 WhatIf tests
- [ ] PATCH is never called during WhatIf
- [ ] GET is still called during WhatIf

### Task 5: Verification and result object tests

**Action:** Describe blocks for post-PATCH verification and result structure.

**Verification tests:**
1. `Re-reads settings after PATCH` — verify GET called at least twice (before and after)
2. `Sets Verified = $true when post-PATCH values match` — mock post-PATCH GET to return expected values
3. `Sets Verified = $false when post-PATCH values differ` — mock post-PATCH GET to return different values

**Result object tests:**
4. `Returns PSCustomObject with expected properties` — verify Metadata, Applied, PreviousConfig, NewConfig, Verified, AuditRecord
5. `PreviousConfig captures pre-PATCH state` — verify PreviousConfig matches mock disabled response
6. `NewConfig captures post-PATCH state` — verify NewConfig matches target values
7. `Metadata includes EnvironmentName` — verify Metadata.EnvironmentName

**Acceptance criteria:**
- [ ] 7 tests covering verification and result structure
- [ ] Verified flag correctly reflects post-PATCH validation

### Task 6: Dataverse audit record tests

**Action:** Describe block for optional Dataverse audit record writing.

**Tests:**
1. `Without -DataverseUrl, does not attempt Dataverse write` — mock Invoke-RestMethod, verify no Dataverse API calls
2. `With -DataverseUrl, writes compliance record` — mock Dataverse POST, verify called with correct entity path and payload
3. `Audit record contains before/after values` — capture POST body, verify `fsi_notes` includes before and after values
4. `Audit record contains timestamp` — verify `fsi_lastscandate` is present and ISO 8601 format
5. `Dataverse write failure does not block result` — mock Dataverse POST to throw, verify script still returns result with Applied = $true

**Mock strategy:**
- Add method + URI parameter filters to distinguish BAP API calls (`api.bap.microsoft.com`) from Dataverse calls (`crm.dynamics.com`)
- Capture Dataverse POST body for assertion

**Acceptance criteria:**
- [ ] 5 Dataverse audit tests
- [ ] Tests verify both "with" and "without" DataverseUrl scenarios
- [ ] Failure isolation test confirms remediation succeeds even when Dataverse write fails
