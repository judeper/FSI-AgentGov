# Plan 02-01: Script Core + 6 Publishing Criteria Validation

## Objective

Create `restrict-agent-publishing.ps1` with PowerShell 7.0 conventions, validating 6 publishing restriction criteria with zone-based logic for agent publishing governance.

## Tasks

### Task 1: Script Scaffolding and Parameters

**Action:** Create `scripts/governance/restrict-agent-publishing.ps1` with comment-based help, `#Requires` directives, and parameter block.

**Details:**
- Comment-based help with `.SYNOPSIS`, `.DESCRIPTION`, `.PARAMETER`, `.EXAMPLE`, `.OUTPUTS`, `.NOTES`
- `.SYNOPSIS`: "Validates agent publishing restriction governance across 6 criteria."
- `.DESCRIPTION`: Explain 6 criteria (env maker role removal, authorized security groups, share with everyone disabled, DLP connector blocking, managed environment sharing limits, approval workflow active for Zone 2/3). Reference Control 1.1, 2.1, 3.7.
- `#Requires -Version 7.0`
- `#Requires -Modules @{ ModuleName = 'Microsoft.PowerApps.Administration.PowerShell'; ModuleVersion = '2.0.0' }`
- Parameters (identical convention to existing scripts):
  - `$OutputFormat` — ValidateSet('Table', 'JSON', 'Object'), default 'Table'
  - `$OutputPath` — optional file path for JSON export
  - `$EnvironmentFilter` — optional string array to limit scope
  - `$ZoneMapping` — optional hashtable mapping env names to zone numbers
  - `$IncludeEvidence` — switch for SHA-256 integrity hashing
- `[CmdletBinding(SupportsShouldProcess)]`
- `$ErrorActionPreference = 'Stop'`
- Banner: cyan box drawing — "FSI Agent Governance — Publishing Restriction Check"
- WhatIf preview: "Would check 6 publishing restriction criteria across Power Platform environments"

**Acceptance criteria:**
- Script loads without parse errors in PowerShell 7.0+
- All parameters have validation attributes matching established pattern
- Help text is complete with at least 3 examples

### Task 2: Helper Functions

**Action:** Implement helper functions for zone mapping and result building.

**Details:**
- `Get-EnvironmentZone` — returns zone number from `$ZoneMapping` hashtable (default Zone 1). Same implementation as existing scripts.
- `New-PublishingCheckResult` — creates standardized PSCustomObject:
  - `CriterionNumber` (1-6)
  - `Setting` (human-readable name)
  - `CheckGroup` (TenantSettings/EnvironmentRoles/DLPPolicy/ApprovalWorkflow)
  - `Status` (Pass/Fail/Skip/Warning)
  - `Expected` (what the policy requires)
  - `Actual` (current configuration value)
  - `Environment` (environment name, or "Tenant" for tenant-level)
  - `Zone` (governance zone number)
  - `Message` (additional context)
  - `EvidenceHash` ($null, populated later if -IncludeEvidence)

**Acceptance criteria:**
- `Get-EnvironmentZone` returns correct zone or default 1
- `New-PublishingCheckResult` produces consistent objects matching existing result patterns

### Task 3: Tenant-Level Check — Criterion 3 (Share with Everyone)

**Action:** Implement Check Group 1 — tenant-level "Share with Everyone" toggle validation.

**Details:**
- Call `Get-TenantSettings`
- Check `powerPlatform.powerApps.disableShareWithEveryone` (primary path)
- Also attempt `powerPlatform.copilotStudio.shareWithEveryoneDisabled` (fallback path)
- Zone logic:
  - Zone 1: Warning if enabled (recommended to disable)
  - Zone 2/3: Fail if not disabled
- Since tenant-wide, create one result per zone group represented in `$ZoneMapping`
  - If no zone mapping provided, evaluate as Zone 1 (default — Warning)
- Error handling: `try/catch`, Skip status on API failure
- Add gap string if Fail

**Acceptance criteria:**
- Correctly reads tenant setting for share-with-everyone toggle
- Zone-based logic differentiates warning vs. fail
- Graceful handling of missing property paths

### Task 4: Per-Environment Checks — Criteria 1, 2, 5

**Action:** Implement Check Group 2 — per-environment publishing restriction validation.

**Details:**
- Enumerate environments via `Get-AdminPowerAppEnvironment`
- Apply `$EnvironmentFilter` if specified (same filtering pattern as HardeningBaseline)
- For each environment, determine zone via `Get-EnvironmentZone`

**Criterion 1 — Environment Maker Role Removal:**
- Call `Get-AdminPowerAppEnvironmentRoleAssignment -EnvironmentName $envId`
- Check for "All Users" principal (`PrincipalObjectId` matching well-known ID or display name)
- Also check for org-wide groups with Environment Maker role
- Zone 1: Warning if All Users has role; Zone 2/3: Fail
- Pass if no broad group has Environment Maker role

**Criterion 2 — Authorized Security Groups:**
- Read `$env.Internal.properties.securityGroupId`
- If no security group assigned: Zone 1 = Pass (advisory), Zone 2/3 = Fail
- If security group assigned: report group ID as Actual value
- Optionally attempt Graph API resolution for group name (best-effort, not required):
  ```powershell
  try {
      $token = Get-AzAccessToken -ResourceUrl 'https://graph.microsoft.com' -ErrorAction Stop
      $group = Invoke-RestMethod -Uri "https://graph.microsoft.com/v1.0/groups/$securityGroupId" `
          -Headers @{ Authorization = "Bearer $($token.Token)" } -ErrorAction Stop
      $groupName = $group.displayName
  } catch {
      $groupName = "(unable to resolve — verify manually)"
  }
  ```
- Report whether group name matches `FSI-Agent-Makers-*` pattern (informational, not enforced)

**Criterion 5 — Managed Environment Sharing Limits:**
- Read `$env.Internal.properties.governanceConfiguration`
- Check `protectionLevel` for Managed Environment status
- Read sharing limit from `settings.extendedSettings` or related property
- Zone thresholds:
  - Zone 1: No limit required, but recommend Managed Environment enabled → Warning if not
  - Zone 2: Sharing limit ≤ 20 → Fail if exceeded or not configured
  - Zone 3: Sharing limit ≤ 5 → Fail if exceeded; Fail if not Managed Environment
- Handle missing `governanceConfiguration` gracefully (Skip if property doesn't exist)

**Acceptance criteria:**
- All 3 criteria produce results for every scanned environment
- Zone logic correctly applied per criterion
- Missing API properties result in Skip, not crash
- Progress output via `Write-Verbose`

### Task 5: DLP Policy Check — Criterion 4

**Action:** Implement Check Group 3 — DLP connector blocking validation.

**Details:**
- Call `Get-AdminDlpPolicy` to retrieve all DLP policies
- For each policy, examine connector classifications:
  - `connectorGroups` with `classification` = 'Blocked'
  - Look for connectors related to agent publishing (by connector ID or display name):
    - "Microsoft Copilot Studio" connector
    - "HTTP" connector
    - "HTTP Webhook" connector
- Determine whether policy applies to the target environment(s)
- Zone logic:
  - Zone 1: Pass (DLP not required for personal productivity)
  - Zone 2/3: Fail if no policy blocks agent publishing connectors
- This check is **semi-automated**: the script validates that a DLP policy exists with blocked connectors covering the environment, but exact connector matching may require manual verification

**Acceptance criteria:**
- Retrieves DLP policies without error
- Reports which policies apply to which environments
- Correctly identifies blocked connector groups
- Semi-automated status communicated in result message

### Task 6: Approval Workflow Check — Criterion 6

**Action:** Implement Check Group 4 — approval workflow validation (Zone 2/3 only).

**Details:**
- Only runs for environments in Zone 2 or Zone 3
- Zone 1 environments: auto-Pass with message "Approval workflow not required for Zone 1"
- **Semi-automated check approach:**
  1. Check environment `governanceConfiguration` for maker onboarding settings (proxy for approval process)
  2. Attempt to detect Power Automate flows with naming patterns matching approval workflows:
     ```powershell
     try {
         $flows = Get-AdminFlow -EnvironmentName $envId -ErrorAction Stop
         $approvalFlows = $flows | Where-Object {
             $_.DisplayName -match 'agent.*publish.*approval|publishing.*approval|maker.*request'
         }
     } catch {
         # Flow enumeration not available — report as semi-automated
     }
     ```
  3. If maker onboarding configured OR approval flow found: Pass
  4. If neither found: Fail (Zone 2/3) with message to verify manually
  5. Always include "Semi-Automated" qualifier in result message

**Acceptance criteria:**
- Zone 1 environments get auto-Pass
- Zone 2/3 environments check for approval indicators
- Graceful fallback when flow enumeration fails
- Clear messaging about semi-automated nature
