# Plan 03-02: Adaptive Card Template, Power Automate Flow JSON, and Flow Setup Guide

## Goal

Create the complete automation layer that ties the runbook wrapper (03-01), Dataverse infrastructure (Phase 2), and operator alerting into a daily automated workflow. The flow JSON is the orchestration backbone — it triggers daily, executes the runbook, parses results, writes to Dataverse for audit trail, and routes alerts based on severity. The adaptive card provides rich Teams notifications. The setup guide ensures operators can deploy and configure the flow.

## Tasks

### Task 1: Create adaptive-card-access-alert.json

Create `agent-access-monitor/src/adaptive-card-access-alert.json` following the SSC/ACV adaptive card pattern.

**Card structure:**

```
┌─────────────────────────────────────────┐
│ ⚠ AGENT ACCESS GOVERNANCE MONITOR      │
│ Severity: ${AlertSeverity}              │
├─────────────────────────────────────────┤
│ Run Summary                             │
│ Time: ${Timestamp}                      │
│ Total Environments: ${TotalEnvironments}│
│ Status: ${OverallStatus}                │
│ Reason: ${Reason}                       │
├─────────────────────────────────────────┤
│ Zone Summary                            │
│ Zone 1: ${Z1Compliant}/${Z1Total}       │
│ Zone 2: ${Z2Compliant}/${Z2Total}       │
│ Zone 3: ${Z3Compliant}/${Z3Total}       │
├─────────────────────────────────────────┤
│ Violations (if any)                     │
│ • ${ViolationEnvironment} (Zone ${Zone})│
│   Setting: ${Setting}                   │
│   Expected: ${Expected}                 │
│   Actual: ${Actual}                     │
│   Severity: ${Severity}                 │
├─────────────────────────────────────────┤
│ Drift Detection                         │
│ Drifted Environments: ${DriftCount}     │
│ • ${DriftEnv}: ${DriftSetting}          │
│   Baseline: ${BaselineValue}            │
│   Current: ${CurrentValue}              │
│   Direction: ${Direction}               │
├─────────────────────────────────────────┤
│ [View in Power Platform Admin]          │
│ [Run Manual Check] [View Documentation] │
└─────────────────────────────────────────┘
```

**Design rules:**
- Adaptive Card schema version 1.4
- Use `${variableName}` convention for all dynamic values
- Severity drives accent color: Critical=attention(red), High=warning(orange), Info=accent(blue)
- Use `ColumnSet` for zone summary table layout
- Use `FactSet` for violation details
- Action buttons use `Action.OpenUrl` with configurable target URLs
- Card must be valid JSON parseable by Power Automate

**Acceptance Criteria:**
- [ ] Valid Adaptive Card JSON (schema 1.4)
- [ ] All dynamic values use `${variableName}` convention
- [ ] Contains sections: header, run summary, zone summary, violations, drift, actions
- [ ] Severity badge uses appropriate colors
- [ ] Action buttons point to Power Platform Admin Center and documentation

### Task 2: Create access-validation-flow.json

Create `agent-access-monitor/src/access-validation-flow.json` — the Power Automate cloud flow definition.

**Flow structure:**

```
Trigger: Recurrence (Daily, 6:00 AM UTC)
│
├── Initialize_Variables
│   ├── var_DataverseUrl (string)
│   ├── var_TeamsGroupId (string)
│   ├── var_TeamsChannelId (string)
│   ├── var_RunbookName (string = "Start-AccessValidationRunbook")
│   └── var_AutomationAccount (string)
│
├── Scope_Try
│   ├── Create_Automation_Job
│   │   └── Azure Automation: Create Job
│   │       - RunbookName: var_RunbookName
│   │       - Parameters: TenantId, ClientId, CertificateThumbprint, DataverseUrl
│   │
│   ├── Wait_For_Job
│   │   └── Azure Automation: Get Job → Until Status = Completed/Failed
│   │
│   ├── Get_Job_Output
│   │   └── Azure Automation: Get Job Output
│   │
│   ├── Parse_Results
│   │   └── Parse JSON (schema matches runbook output)
│   │
│   ├── Write_Validation_History
│   │   └── HTTP POST to {DataverseUrl}/api/data/v9.2/fsi_accessvalidationhistories
│   │       - fsi_name: "Scan-{Timestamp}"
│   │       - fsi_runid: new GUID
│   │       - fsi_overallstatus: OverallStatus
│   │       - fsi_violationcount: Violations.length
│   │       - fsi_totalenvironments: TotalEnvironments
│   │       - fsi_summaryjson: full JSON output
│   │       - fsi_timestamp: Timestamp
│   │       runAfter: Parse_Results [Succeeded]
│   │
│   ├── Check_Alert_Required
│   │   └── Condition: AlertRequired = true
│   │       runAfter: Write_Validation_History [Succeeded, Failed]
│   │
│   ├── If_Alert_Required_True
│   │   ├── Check_Severity_Level
│   │   │   └── Condition: AlertSeverity in (Critical, Failed)
│   │   │
│   │   ├── If_Critical
│   │   │   ├── Post_Teams_Card
│   │   │   │   └── Teams: Post adaptive card (replace ${} vars)
│   │   │   │       connection: fsi_cr_teams_accessmonitor
│   │   │   └── Send_Alert_Email
│   │   │       └── Office 365: Send email with violation summary
│   │   │           connection: fsi_cr_office365_accessmonitor
│   │   │
│   │   └── If_High_Warning
│   │       └── Send_Warning_Email
│   │           └── Office 365: Send email only
│   │
│   └── If_Alert_Required_False
│       └── (no action — scan passed, history already written)
│
└── Scope_Catch
    └── Send_Critical_Error_Email
        └── Office 365: Send CRITICAL error email
            - Subject: "CRITICAL: AAM Flow Execution Failed"
            - Body: error details from Scope_Try
            runAfter: Scope_Try [Failed, TimedOut]
```

**Key design decisions:**
- Write_Validation_History is BEFORE Check_Alert_Required (learned from SSC gap)
- Check_Alert_Required runs after Write_Validation_History with `[Succeeded, Failed]` — alerting proceeds even if the Dataverse write fails
- Connection references use existing `fsi_cr_dataverse_accessmonitor` and `fsi_cr_teams_accessmonitor`
- Parse_Results JSON schema matches the runbook output schema from Plan 03-01
- Flow uses Azure Automation connector for runbook execution

**Acceptance Criteria:**
- [ ] Valid Power Automate flow JSON importable into Power Automate
- [ ] Daily recurrence trigger at 6:00 AM UTC
- [ ] Scope_Try/Scope_Catch error handling pattern
- [ ] Write_Validation_History action writes to Dataverse after every scan
- [ ] Alert routing: Critical → Teams + email; High/Warning → email; Passed → none
- [ ] Scope_Catch sends CRITICAL error email on flow failure
- [ ] Connection references match Phase 2 deployed references
- [ ] Parse_Results schema matches runbook JSON output

### Task 3: Create FLOW_SETUP.md

Create `agent-access-monitor/docs/FLOW_SETUP.md` — step-by-step guide for operators.

**Document structure:**

1. **Prerequisites**
   - Azure Automation account with runbook deployed
   - Power Automate Premium license (Azure Automation connector)
   - Phase 2 Dataverse schema deployed
   - Connection references configured
   - Teams channel for alerts

2. **Import the Flow**
   - Download `access-validation-flow.json`
   - Navigate to Power Automate → My Flows → Import
   - Select JSON file and configure

3. **Configure Variables**
   - `var_DataverseUrl`: Dataverse environment URL
   - `var_TeamsGroupId`: Teams group ID for alert channel
   - `var_TeamsChannelId`: Teams channel ID
   - `var_RunbookName`: Azure Automation runbook name
   - `var_AutomationAccount`: Azure Automation account resource

4. **Bind Connection References**
   - `fsi_cr_dataverse_accessmonitor` → Dataverse connection
   - `fsi_cr_teams_accessmonitor` → Teams connection
   - `fsi_cr_office365_accessmonitor` → Office 365 connection

5. **Test the Flow**
   - Manual trigger test
   - Verify Dataverse history write
   - Verify Teams alert delivery
   - Check Azure Automation job output

6. **Troubleshooting**
   - Dataverse write failures (permissions, schema)
   - Azure Automation timeout
   - Teams channel not found
   - Parse JSON schema mismatch

**Acceptance Criteria:**
- [ ] Complete step-by-step instructions from import to test
- [ ] Connection reference binding documented
- [ ] Troubleshooting covers common failure modes
- [ ] Screenshots placeholder references (EXPECTED.md format)
