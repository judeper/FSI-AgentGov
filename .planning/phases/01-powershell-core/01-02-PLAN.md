    Create Deploy-AuthContexts.ps1 following CAA Deploy-CAPolicies.ps1 structure exactly. READ the CAA script first for parameter handling, banner format, error collection, and summary output patterns.

    **Script header:**
    - `#Requires -Version 7.0`
    - `#Requires -Modules Microsoft.Graph.Identity.SignIns`
    - Comment-based help (.SYNOPSIS, .DESCRIPTION, .PARAMETER, .EXAMPLE) following CAA pattern
    - Set-StrictMode -Version Latest, $ErrorActionPreference = "Stop"

    **Parameters (CmdletBinding):**
    - `-TenantId` [string] Mandatory — Azure AD tenant ID
    - `-Interactive` [switch] — Use interactive browser auth
    - `-ClientId` [string] — For service principal auth
    - `-CertificateThumbprint` [string] — For service principal auth
    - `-TemplatePath` [string] default "$PSScriptRoot\..\templates\auth-contexts\auth-contexts-c1-c5.json" — Path to auth context definitions
    - `-AuthContextPrefix` [string] default "" — Optional prefix offset (e.g., "c10" to use c10-c14 instead of c1-c5 if c1-c5 already in use)
    - `-DryRun` [switch] — Preview changes only
    - `-Force` [switch] — Overwrite existing auth contexts with different names

    **Initialization:**
    - Cyan banner: "Session Security Configurator - Authentication Context Deployment" + "FSI-AgentGov Control 1.23"
    - Display: TenantId, Mode (DRY RUN or DEPLOY), Force status

    **Logic flow:**
    1. Load auth context template JSON from TemplatePath
    2. If AuthContextPrefix specified, remap IDs (c1->c10, c2->c11, etc.)
    3. Dot-source and call Connect-GraphSession (skip if DryRun)
    4. Query existing auth contexts: `Get-MgIdentityConditionalAccessAuthenticationContextClassReference`
    5. For each context in template:
       a. Check if ID already exists
       b. If exists with SAME displayName: skip (idempotent), log as "Already configured"
       c. If exists with DIFFERENT displayName: conflict detected
          - Without -Force: abort ALL deployment, throw error listing conflicts. Message: "Auth context {id} exists with description '{existing}'. FSI-AgentGov expects '{expected}'. Use -Force to overwrite or -AuthContextPrefix to use different IDs."
          - With -Force: update existing context, log as "Updated (forced)"
       d. If not exists: create new, log as "Created"
       e. If DryRun: log "[DRY RUN] Would create/update auth context {id}" in Yellow
    6. Collect results in `$deployedContexts` array with Status (Created/Updated/Skipped/Conflict/DryRun)
    7. Collect errors in `$errors` array

    **Summary output:**
    - Follow CAA summary format: "=" banner, count of contexts processed
    - Color-coded status per context (Green=Created, Yellow=Updated/Skipped, Gray=DryRun, Red=Error)
    - Error list if any
    - Return structured results object for downstream use

    **Critical requirements:**
    - ABORT on first conflict if -Force not specified (SCM-01: "aborts with a clear warning")
    - DryRun must NOT call Connect-MgGraph or any Graph write APIs
    - Use Graph SDK cmdlets (New-MgIdentityConditionalAccessAuthenticationContextClassReference, Update-MgIdentityConditionalAccessAuthenticationContextClassReference)
  </action>

    Create Deploy-StepUpPolicies.ps1 following CAA Deploy-CAPolicies.ps1 structure. This is the most complex script in the solution. READ the CAA script first for the template processing, config substitution, and deployment loop patterns.

    **Script header:**
    - `#Requires -Version 7.0`
    - `#Requires -Modules Microsoft.Graph.Identity.SignIns`
    - Full comment-based help following CAA pattern

    **Parameters (CmdletBinding):**
    - `-TenantId` [string] Mandatory
    - `-ConfigPath` [string] Mandatory — Path to tenant config JSON (groups, breakGlassAccounts, authStrengthPolicies)
    - `-Zone` [ValidateSet("All", "Zone1", "Zone2", "Zone3")] default "All"
    - `-TemplatePath` [string] default "$PSScriptRoot\..\templates\step-up"
    - `-Interactive` [switch]
    - `-ClientId` [string]
    - `-CertificateThumbprint` [string]
    - `-EnablePolicies` [switch] — Transition from report-only to enforced (DANGEROUS)
    - `-DryRun` [switch]
    - `-Force` [switch] — Update existing policies
    - `-SkipConflictAudit` [switch] — Skip CA policy conflict check (not recommended)

    **Config file structure expected:**
    ```json
    {
      "tenantId": "...",
      "groups": { "zone1Users": "guid", "zone2Users": "guid", "zone3Users": "guid" },
      "breakGlassAccounts": ["guid1", "guid2"],
      "authStrengthPolicies": { "passwordlessMFA": "guid", "phishingResistantMFA": "guid" },
      "policyPrefix": "SSC"
    }
    ```

    **Logic flow:**

    1. **Banner** — Cyan, "Session Security Configurator - Step-Up Policy Deployment", Control 1.23
    2. **Load + validate config** — Required fields: tenantId, groups, breakGlassAccounts, authStrengthPolicies. Abort if missing.
    3. **Determine templates** — Map Zone param to template files (zone1/2/3-step-up-policy.json). "All" deploys all three.
    4. **72-hour bake period enforcement (SCM-07):**
       - If `-EnablePolicies` is specified:
         a. Connect to Graph, query existing SSC policies by displayName prefix
         b. For each policy, check `createdDateTime`
         c. If ANY policy was created < 72 hours ago: ABORT with error "Policy '{name}' was created {hours}h ago. Minimum 72-hour report-only bake period required. Earliest enforcement: {datetime}."
         d. If all policies are 72+ hours old: prompt confirmation "WARNING: {N} policies will be transitioned from report-only to enforced. This will actively block non-compliant sessions. Continue? [y/N]"
         e. On confirmation: update each policy state to "enabled"
         f. Return after enforcement — do NOT also deploy new policies
    5. **Pre-deployment CA policy conflict audit (Success Criteria 5):**
       - Unless `-SkipConflictAudit`, query ALL existing CA policies: `Get-MgIdentityConditionalAccessPolicy`
       - For each template being deployed, check for overlapping policies:
         a. Same includeGroups targeting (overlapping user groups)
         b. Different sessionControls.signInFrequency values
         c. Same includeApplications targeting
       - If conflicts found: display warning table with policy name, conflict type, and impact
       - Do NOT abort on conflicts (operator may intentionally have overlapping policies) — warn only
       - If `-DryRun`: show conflict audit results and stop
    6. **Template processing** — For each template (following CAA Deploy-CAPolicies.ps1 pattern exactly):
       a. Load JSON, convert to hashtable
       b. Substitute placeholders: group IDs from config, break-glass accounts from config, auth strength policy IDs from config
       c. Apply policyPrefix if configured
       d. Force state to "enabledForReportingButNotEnforced" (never deploy as enabled — SCM-07)
       e. **Break-glass validation** — dot-source and call `Test-BreakGlassExclusion` for each policy. If validation fails: ABORT entire deployment immediately.
    7. **Zone 3 Beta API handling:**
       - If deploying Zone 3 AND template contains signInFrequency of 1h:
         a. Deploy the standard Zone 3 policy using v1.0 API
         b. Additionally create the risky-user reauthentication policy using Beta API:
            - `Import-Module Microsoft.Graph.Beta.Identity.SignIns`
            - Set frequencyInterval: "everyTime", authenticationType: "primaryAndSecondaryAuthentication"
            - Use `New-MgBetaIdentityConditionalAccessPolicy`
            - displayName: "SSC-Zone3-Risky-User-Reauthentication"
       - Log clearly which API is used: "[v1.0 API]" or "[Beta API]"
    8. **Deployment** — For each processed template:
       a. Check existing policy by displayName (idempotent)
       b. If exists + Force: update. If exists + no Force: skip with warning.
       c. If not exists: create via `New-MgIdentityConditionalAccessPolicy`
       d. If DryRun: log preview only
    9. **Summary** — Follow CAA summary format. Include:
       - Policies processed count
       - Per-policy status (Created/Updated/Skipped/DryRun)
       - Conflict audit results (if any warnings)
       - Next steps: "Policies deployed in report-only mode. Wait 72 hours, review sign-in logs, then re-run with -EnablePolicies to enforce."

    **Critical safety requirements:**
    - NEVER deploy policies with state "enabled" during initial deployment
    - ALWAYS validate break-glass exclusions before EVERY policy creation/update
    - 72-hour check uses policy createdDateTime from Graph API, not local timestamps
    - Zone 3 risky user policy MUST use Beta API for everyTime
    - Conflict audit runs BEFORE deployment, not after
