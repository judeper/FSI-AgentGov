**Test-EnvironmentAudit.ps1 (EVAL-01, EVAL-05):**
Validates that Dataverse audit is enabled for a specific Power Platform environment.

Requirements:
- #Requires -Version 7.0
- Comment-based help (.SYNOPSIS, .DESCRIPTION, .PARAMETER, .EXAMPLE)
- Function Test-EnvironmentAudit with parameters:
  - -EnvironmentUrl (mandatory, string) — Dataverse instance URL (e.g., https://org.crm.dynamics.com)
  - -AccessToken (mandatory, string) — Dataverse bearer token
  - -EnvironmentName (optional, string) — Display name for reporting
  - -GracePeriodHours (optional, int, default 24) — Hours after enablement before alerting

Validation checks:
1. **Dataverse exists check**: GET {EnvironmentUrl}/api/data/v9.2/organizations?$select=organizationid,isauditenabled,createdon
   - If request fails with 404 or connection error: return Error status "No Dataverse database accessible"
2. **Audit enablement check**: Check isauditenabled field on Organization record
   - If false: return Failed status, RawValue="AuditEnabled=false", RemediationHint="Enable Dataverse auditing in Power Platform admin center > Environments > {name} > Settings > Auditing"
   - If true: check enablement timing for grace period
3. **Grace period check (EVAL-05)**: If audit is enabled, check if it was recently enabled
   - Query audit log for the most recent "Enable Audit" system event OR check the organization's audit settings modification date
   - If enablement occurred within GracePeriodHours: return GracePeriod status, Reason="Audit enabled {hours}h ago, within {GracePeriodHours}h grace period"
   - If enablement is older than GracePeriodHours: return Passed status
   - NOTE: Grace period detection is best-effort. If enablement timestamp cannot be determined (no audit events yet), treat as Passed with a Warning note rather than Failed (avoid false positives per Phase 1 principle)

Return PSCustomObject matching Phase 1 pattern:
- Timestamp (UTC ISO 8601)
- ValidationType = "EnvironmentAudit"
- EnvironmentId, EnvironmentName
- Checks (hashtable with AuditEnabled, GracePeriod sub-results)
- OverallStatus ("Passed", "GracePeriod", "Failed", "Error")
- Confidence ("High" if API responded cleanly, "Medium" if grace period check was best-effort)
- Reason (human-readable summary)
- RawValue (string of actual values checked)
- RemediationHint (suggestion if failed)

**Test-EnvironmentRetention.ps1 (EVAL-02, EVAL-03):**
Validates per-environment audit retention period against zone-specific thresholds.

Requirements:
- #Requires -Version 7.0
- Comment-based help
- Function Test-EnvironmentRetention with parameters:
  - -EnvironmentUrl (mandatory, string)
  - -AccessToken (mandatory, string)
  - -DataverseUrl (mandatory, string) — Central Dataverse URL where env vars are stored
  - -CentralAccessToken (mandatory, string) — Token for central Dataverse (may differ from environment token)
  - -Zone (mandatory, ValidateSet "Zone1", "Zone2", "Zone3")
  - -EnvironmentName (optional, string)

Validation flow:
1. **Read zone threshold from Dataverse environment variable (EVAL-03):**
   - GET {DataverseUrl}/api/data/v9.2/environmentvariabledefinitions?$filter=schemaname eq 'fsi_ACV_{Zone}RetentionDays'&$select=schemaname,defaultvalue
   - Also check environmentvariablevalues for instance-specific override
   - Parse threshold as integer (e.g., Zone1=180, Zone2=365, Zone3=730)
   - If env var not found: use hardcoded fallback (180/365/730) but log warning "Environment variable fsi_ACV_{Zone}RetentionDays not found, using default {value}"

2. **Query environment retention settings (EVAL-02):**
   - Query Dataverse Organization table: GET {EnvironmentUrl}/api/data/v9.2/organizations?$select=organizationid,auditretentionperiodv2,isauditenabled
   - The auditretentionperiodv2 field contains retention period in days (documented in research as Organization table extended property)
   - NOTE (Open Question from research): If auditretentionperiodv2 is not available or returns null, try alternative: query via Get-AdminPowerAppEnvironment properties if accessible. If neither works, return Warning status with Reason="Unable to determine retention period programmatically. Verify manually in Power Platform admin center."

3. **Compare against threshold:**
   - If retention >= threshold: Passed, RawValue="RetentionDays={actual},RequiredDays={threshold}"
   - If retention < threshold: Failed, RawValue same format, RemediationHint="Increase audit retention to {threshold} days minimum for {Zone} in Power Platform admin center > Environments > {name} > Settings > Auditing"
   - If retention is null/unknown: Warning (not Failed — avoid false positives)

Return PSCustomObject same structure as Test-EnvironmentAudit (Timestamp, ValidationType="EnvironmentRetention", Checks, OverallStatus, Confidence, Reason, RawValue, RemediationHint).

Both validators: Use regulatory-safe language. No "ensures", "guarantees", "will prevent", "eliminates risk".

**Invoke-EnvironmentAuditValidation.ps1:**
Main orchestrator for environment-level audit validation. Runs discovery, then validates each environment, storing all results in Dataverse with a correlated run ID. Mirrors the pattern from Invoke-TenantAuditValidation.ps1 (Phase 1 orchestrator).

Requirements:
- #Requires -Version 7.0
- #Requires -Modules @{ModuleName="Microsoft.PowerApps.Administration.PowerShell"; ModuleVersion="2.0"}
- Comment-based help with examples for both interactive and service principal usage
- Dot-source: Connect-PowerPlatform.ps1, Write-ValidationResult.ps1, Invoke-EnvironmentDiscovery.ps1, Test-EnvironmentAudit.ps1, Test-EnvironmentRetention.ps1

Parameters:
- -TenantId (mandatory)
- -DataverseUrl (mandatory) — Central Dataverse URL for registry and history
- -ClientId (optional), -ClientSecret (optional SecureString), -CertificateThumbprint (optional), -Interactive (switch)
- -IncludeTrialDev (switch) — pass through to discovery
- -GracePeriodHours (optional, int, default 24)
- -OutputPath (optional) — write full results JSON to file
- -SkipDiscovery (switch) — use existing registry without re-scanning (for faster repeat runs)

**Execution flow:**

1. **Initialize**: Generate RunId (New-Guid), record start time, authenticate via Connect-PowerPlatform

2. **Discovery phase** (unless -SkipDiscovery):
   - Call Invoke-EnvironmentDiscovery with auth params
   - Log discovery summary: "{N} environments found, {M} new, {K} to validate"
   - If no environments in validation set: Write-Warning and return early

3. **Validation phase** (for each environment in validation set):
   - Acquire Dataverse token for the target environment URL (may need separate token per environment)
   - Execute Test-EnvironmentAudit with environment URL and token
     - Wrap in try-catch (isolated execution — one env failure doesn't block others, per Phase 1 pattern)
   - Execute Test-EnvironmentRetention with environment URL, token, zone, and central Dataverse URL/token
     - Wrap in try-catch
   - Compute per-environment overall status using Phase 1 priority logic: Error/Failed > Warning/GracePeriod > Passed
   - Call Write-ValidationResult for each check result (2 records per environment: audit + retention)
   - Also call Write-ValidationResult once with scope=Environment and ValidationType="Orchestrator" for the per-environment overall status
   - Update fsi_lastvalidated on the environment registry record (PATCH)

4. **Aggregate results**:
   - Compute overall run status across all environments (same priority logic)
   - Build results object: RunId, Timestamp, TotalEnvironments, PerEnvironmentResults (array), OverallStatus

5. **Console output** (same colored table pattern as Invoke-TenantAuditValidation.ps1):
   - Box-drawing header: "Environment Audit Validation Results"
   - Per-environment rows: Name | Zone | Audit Status | Retention Status | Overall
   - Color-coded: Green=Passed, Yellow=Warning/GracePeriod, Red=Failed/Error
   - Summary row: "Overall: {status} ({passed}/{total} environments passed)"
   - If new/unclassified environments found, print warning section

6. **Output**: If -OutputPath, export complete results as JSON. Return results object.

Key design decisions:
- RunId is shared across ALL Write-ValidationResult calls in this execution (tenant + env), enabling correlated queries
- Each environment gets its own try-catch block so one environment failure doesn't halt the entire run (Phase 1 pattern)
- Token acquisition per environment is wrapped separately since different environments may have different Dataverse URLs
- Zone thresholds are NOT passed as parameters — validators read them from Dataverse env vars (fsi_ACV_*) per user decision

Use regulatory-safe language throughout. No "ensures", "guarantees", "will prevent", "eliminates risk".
