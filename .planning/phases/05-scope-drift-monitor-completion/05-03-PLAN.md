# Flow Configuration Guide

Configuration guide for Scope Drift Monitor Power Automate flows.

---

## Overview

The Scope Drift Monitor includes three Power Automate flows:

| Flow | Purpose | Trigger |
|------|---------|---------|
| SDM-DriftDetector | Detect out-of-scope access | Scheduled (15 minutes) |
| SDM-AlertDispatcher | Send violation notifications | Dataverse row created |
| SDM-ExpansionProcessor | Process scope expansion requests | Dataverse row created |

---

## Prerequisites

Before configuring flows:

1. Import the ScopeDriftMonitor solution
2. Configure connection references (see below)
3. Set environment variable values

---

## Connection References

Configure these connections during solution import or post-import:

| Connection | Required Permissions |
|------------|---------------------|
| **Dataverse** | Read/Write access to fsi_* tables |
| **Office 365 Outlook** | Send mail on behalf of user |
| **Microsoft Teams** | Post to channel |
| **HTTP with Azure AD** | Office 365 Management API (audience: https://manage.office.com) |
| **Approvals** | Standard approvals access |

### HTTP with Azure AD Configuration

For the DriftDetector flow to query the Unified Audit Log:

1. Create Azure AD app registration with:
   - API Permission: `Office 365 Management APIs > ActivityFeed.Read`
   - Application permission (not delegated)
   - Admin consent granted

2. Configure HTTP connection:
   - Base URL: https://manage.office.com
   - Azure AD Resource: https://manage.office.com
   - Client ID: (from app registration)
   - Tenant: (your tenant ID)

---

## Environment Variables

Set these values after solution import:

| Variable | Required | Description | Example |
|----------|----------|-------------|---------|
| `fsi_SDM_TenantId` | Yes | Azure AD tenant ID | `12345678-...` |
| `fsi_SDM_SecurityTeamEmail` | Yes | Security team email | `security@contoso.com` |
| `fsi_SDM_TeamsChannelId` | No | Teams channel for alerts | `19:...@thread.tacv2` |
| `fsi_SDM_TeamsGroupId` | No | Teams group ID | `12345678-...` |
| `fsi_SDM_DataverseEnvironment` | No | Environment URL | `https://contoso.crm.dynamics.com` |
| `fsi_SDM_DetectionWindowMinutes` | No | Detection window | `15` (default) |

---

## SDM-DriftDetector Configuration

### Detection Window

The flow runs every 15 minutes by default. To change:

1. Edit the flow in Power Automate
2. Select the Recurrence trigger
3. Change `interval` value

**Note:** Shorter intervals increase API call volume. Unified Audit Log has ~90 minute latency, so intervals under 15 minutes provide minimal benefit.

### Graceful Degradation

The flow continues even if some audit sources fail:

- If Unified Audit Log unavailable: logs warning, continues
- Violations still created for any detected drift
- Source status logged for troubleshooting

### Agent Matching

Events are matched to scopes via:
- Agent ID from CopilotInteraction event
- Environment ID from event context

If no matching scope found, a "No Baseline" violation is created.

---

## SDM-AlertDispatcher Configuration

### Teams Channel

To enable Teams alerts:

1. Get Teams group ID and channel ID
2. Set environment variables: `fsi_SDM_TeamsGroupId`, `fsi_SDM_TeamsChannelId`
3. Ensure the connection has permission to post to the channel

### Email Recipients

Alerts are sent to:
- Agent owner (from fsi_agentscope.fsi_owner)
- Security team (from `fsi_SDM_SecurityTeamEmail`)

---

## SDM-ExpansionProcessor Configuration

### Approval Workflow

Expansion requests route to the security team for approval:
- Timeout: 7 days (auto-deny if no response)
- On approval: Agent scope is automatically updated
- On denial: Requestor is notified

### Approval Configuration

To change the approver:
1. Update `fsi_SDM_SecurityTeamEmail` environment variable
2. Supports distribution lists for team approvals

# Troubleshooting Guide

Common issues and solutions for Scope Drift Monitor.

---

## Detection Issues

### No Events Found in Detection Run

**Symptoms:**
- Flow runs successfully but finds 0 events
- No violations created despite known agent activity

**Causes and Solutions:**

| Cause | Solution |
|-------|----------|
| **Audit log latency** | CopilotInteraction events have ~90 minute latency. Wait and retry. |
| **Missing E5 license** | CopilotInteraction events require E5 or E5 Compliance license. |
| **API permission missing** | Verify ActivityFeed.Read permission on app registration. |
| **Subscription not started** | Run: `POST https://manage.office.com/.../subscriptions/start?contentType=Audit.General` |
| **Agent not using Copilot Studio** | Events are for CopilotStudio agents (AppHost=CopilotStudio). M365 Copilot has different event structure. |

### Cannot Match Events to Agents

**Symptoms:**
- Events found but all create "No Baseline" violations
- Agent IDs don't match scope definitions

**Solution:**
1. Verify agent ID in fsi_agentscope.fsi_agentid matches CopilotInteraction event
2. Agent IDs can differ between authoring and runtime; use published agent ID
3. Check environment ID also matches (fsi_environmentid)

### HTTP 403 from Management API

**Symptoms:**
- Flow fails with 403 Forbidden
- Error: "Access denied"

**Solution:**
1. Verify app registration has ActivityFeed.Read permission
2. Ensure admin consent is granted
3. Check tenant ID in environment variable matches app registration tenant

---

## Alert Issues

### Teams Card Not Posting

**Symptoms:**
- Violations created but no Teams alert
- Flow shows succeeded but Teams channel empty

**Solutions:**

| Cause | Solution |
|-------|----------|
| **Missing channel ID** | Set fsi_SDM_TeamsChannelId and fsi_SDM_TeamsGroupId environment variables |
| **Permission denied** | Connection account must be member of the Teams channel |
| **Invalid card JSON** | Check flow run history for Adaptive Card validation errors |

**Note:** Teams incoming webhooks are retiring March 31, 2026. This solution uses Power Automate Teams connector which is not affected.

### Email Not Sending

**Symptoms:**
- No email notifications despite violations

**Solutions:**
- Verify fsi_SDM_SecurityTeamEmail has a valid email address
- Check connection account has "send as" permissions
- Review flow run history for specific errors

---

## Approval Issues

### Expansion Requests Stay Pending

**Symptoms:**
- Requests created but never reach approver
- fsi_status remains 1 (Pending)

**Solution:**
1. Verify SDM-ExpansionProcessor flow is turned on
2. Check fsi_SDM_SecurityTeamEmail is set
3. Review flow run history for trigger failures

### Auto-Deny Not Working

**Symptoms:**
- Old requests (>7 days) still pending

**Solution:**
- The 7-day timeout is processed when the flow times out
- If flow was not running for 7 days, requests may accumulate
- Manually update old requests or wait for next trigger

### Scope Not Updated After Approval

**Symptoms:**
- Request shows Approved but agent still gets violations

**Solutions:**
1. Check flow run history for update failures
2. Verify JSON parsing of allowed arrays succeeded
3. Manually verify fsi_agentscope record was updated

---

## Data Issues

### Duplicate Violations

**Symptoms:**
- Same resource appears in multiple violation records

**Possible causes:**
- Detection window overlap (edge case)
- Same resource accessed multiple times

**Note:** Some duplication is expected. Deduplicate in reporting, not detection.

### JSON Parse Errors

**Symptoms:**
- Flows fail with "Invalid JSON" errors
- Scope records have malformed allowed arrays

**Solution:**
- Ensure allowed arrays are valid JSON: `["item1", "item2"]`
- Use empty array `[]` not empty string for no items
- Validate JSON before saving scope records

---

## Performance Issues

### Detection Flow Timeout

**Symptoms:**
- Flow fails with timeout after long run

**Solutions:**
- Reduce detection window (but not below 15 minutes)
- Check if large number of agents causing slow queries
- Consider filtering to specific agents if too many

### High API Consumption

**Symptoms:**
- Throttling errors from Management API
- "Too many requests" errors

**Solutions:**
- Don't run detection more frequently than every 15 minutes
- Consider longer windows for Zone 1 agents (daily)
- Implement exponential backoff (already in flow)

# Baseline Configuration Guide

Guide for configuring agent scope baselines.

---

## Overview

Each AI agent needs a scope baseline that defines what data sources it is allowed to access. The baseline includes:

- **Connectors** - Power Platform connectors (SharePoint, Dataverse, SQL, etc.)
- **SharePoint Sites** - Specific site URLs
- **Dataverse Tables** - Specific table names
- **External APIs** - Third-party API endpoints

---

## Creating a Baseline

### Option 1: Auto-Generate from Audit History

Use the baseline script to analyze 30 days of agent activity:

```powershell
.\scripts\New-AgentBaseline.ps1 -AgentId "12345678-..." -Environment "https://contoso.crm.dynamics.com" -Days 30
```

This creates a scope definition with:
- Connectors discovered in audit events
- SharePoint sites accessed
- Status: Active (goes live immediately)

**Note:** If no events found, an empty baseline is created. Any subsequent access will trigger a drift violation.

### Option 2: Manual Configuration

Create scope record directly in Dataverse:

1. Navigate to make.powerapps.com > Tables > fsi_agentscope
2. Create new record with:
   - `fsi_name`: Agent display name
   - `fsi_agentid`: Copilot Studio agent ID
   - `fsi_environmentid`: Power Platform environment ID
   - `fsi_zone`: 1 (Personal), 2 (Team), or 3 (Enterprise)
   - `fsi_purpose`: Description of agent's intended use
   - `fsi_status`: 2 (Active)
   - `fsi_allowedconnectors`: JSON array, e.g., `["SharePoint", "Dataverse"]`
   - `fsi_allowedsites`: JSON array, e.g., `["https://contoso.sharepoint.com/sites/KB"]`
   - `fsi_allowedtables`: JSON array, e.g., `["contact", "account"]`
   - `fsi_allowedapis`: JSON array, e.g., `[]`

---

## Scope Definition Fields

### Allowed Connectors

JSON array of connector names:

```json
["SharePoint", "Dataverse", "Office365Users", "AzureBlob"]
```

Connector names should match Power Platform connector names exactly.

### Allowed SharePoint Sites

JSON array of full site URLs:

```json
[
  "https://contoso.sharepoint.com/sites/CustomerKB",
  "https://contoso.sharepoint.com/sites/PublicDocs"
]
```

**Note:** Include full URL including /sites/ path. Library-level filtering is tracked in fsi_scopeitem.

### Allowed Dataverse Tables

JSON array of table logical names:

```json
["contact", "account", "case", "knowledgearticle"]
```

Use logical names (lowercase), not display names.

### Allowed External APIs

JSON array of API base URLs:

```json
[
  "https://api.example.com/v1",
  "https://internal.contoso.com/api"
]
```

Matching is prefix-based; `https://api.example.com/v1` allows all paths under `/v1`.

---

## Scope Status Values

| Status | Value | Description |
|--------|-------|-------------|
| Draft | 1 | Under construction, not monitored |
| Active | 2 | Live monitoring enabled |
| Under Review | 3 | Paused for review |
| Suspended | 4 | Monitoring disabled due to issues |
| Archived | 5 | Agent retired |

Only **Active (2)** scopes are checked during drift detection.

---

## Governance Zones

Zone affects violation severity weighting (future feature):

| Zone | Use Case | Risk Level |
|------|----------|------------|
| Zone 1 - Personal | Individual productivity agents | Low |
| Zone 2 - Team | Departmental collaboration agents | Medium |
| Zone 3 - Enterprise | Org-wide, customer-facing agents | High |

---

## Empty Baselines

Per governance policy, new agents with no established baseline are treated as "monitor everything":

- Empty allowed arrays mean nothing is approved
- Any data access triggers a drift violation
- Use expansion workflow to formally approve access

This is intentional to support principle of least privilege.

---

## Updating Baselines

### Via Expansion Request

When a violation is detected, users can request scope expansion:
1. Violation triggers alert
2. User creates expansion request with justification
3. Security team reviews and approves/denies
4. If approved, scope is automatically updated

### Via Direct Edit

Administrators can edit fsi_agentscope records directly:
1. Navigate to Dataverse table
2. Find agent scope record
3. Modify allowed arrays
4. Save

**Note:** Direct edits bypass approval workflow. Audit changes manually if required.

---

## Best Practices

1. **Start narrow** - Begin with minimal scope, expand as needed
2. **Document purpose** - Use fsi_purpose to explain agent's intended data access
3. **Review periodically** - Set fsi_nextreview for scheduled scope audits
4. **Use Zone 3 for sensitive** - Enterprise agents should have Zone 3 for stricter monitoring
5. **Validate JSON** - Ensure allowed arrays are valid JSON before saving

---
